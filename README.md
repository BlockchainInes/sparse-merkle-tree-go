# Sparse Merkle Tree — Go & Solidity

A 256-bit Sparse Merkle Tree (SMT) implemented in Go, with deterministic Keccak-256 hashing, membership and non-membership proofs, and a Solidity verifier deployed and source-verified on Ethereum Sepolia.

The implementation provides a deterministic commitment structure for key-value state and supports independent verification of proofs across Go and the Ethereum Virtual Machine (EVM).

## Key Capabilities

- 256-bit key space with deterministic root computation
- Keccak-256 hashing compatible with Ethereum
- Domain-separated leaf, internal-node, and empty-leaf hashes
- Membership and non-membership proof generation
- Fixed-depth, 256-sibling Merkle proofs
- Cross-language verification between Go and Solidity
- Deterministic proof vectors generated by the Go implementation
- Unit, negative, randomized, reference, and fuzz testing
- Solidity verifier deployed and verified on Ethereum Sepolia

## Architecture

The repository separates state commitment construction, proof generation, and on-chain proof verification.

| Component | Responsibility |
|---|---|
| `smt/` | Sparse Merkle Tree implementation, hashing, updates, and proof verification in Go |
| `cmd/proofvectors/` | Generation of deterministic proof vectors |
| `test/vectors/go_proofs.json` | Proof fixtures generated by Go |
| `contracts/SparseMerkleVerifier.sol` | Stateless Solidity proof verifier |
| `test/SparseMerkleVerifier.t.sol` | Solidity verification and negative tests |
| `test/GoProofCompatibility.t.sol` | Cross-language verification using Go-generated proofs |
| `foundry.toml` | Solidity compiler and Foundry configuration |

The Go implementation computes the commitment root and produces Merkle proofs. The Solidity contract independently reconstructs the commitment from the supplied key, value, existence flag, and sibling path.

The Solidity verifier does not maintain tree state or store commitment roots. The caller supplies the expected root.

## Cryptographic Construction

### Hash Function

All commitment hashes use legacy Keccak-256, consistent with Ethereum's `keccak256` opcode.

The construction uses explicit domain separation:


| Node Type | Hash Definition |
|---|---|
| Present leaf | `Keccak256(0x00 \|\| key \|\| value)` |
| Internal node | `Keccak256(0x01 \|\| left \|\| right)` |
| Empty leaf | `Keccak256(0x02)` |


Keys, values, and node hashes are represented as 32-byte values.

Internal nodes commit to their ordered left and right children. Domain separation distinguishes leaves, internal nodes, and empty leaves at the hashing layer.

### Empty Subtrees

Empty-subtree commitments are defined recursively:

```text
empty[0] = Keccak256(0x02)

empty[i] = Keccak256(
    0x01 || empty[i-1] || empty[i-1]
)
```

The construction uses a fixed depth of 256 levels.

### Key Ordering

Keys are interpreted as unsigned 256-bit values.

Tree traversal proceeds from the most significant bit toward the least significant bit. Proof reconstruction proceeds in the reverse direction, from leaf to root.

At proof level `i`, the verifier examines bit `i` of the key:

- Bit `0`: the current hash is the left child.
- Bit `1`: the current hash is the right child.

The sibling array contains exactly 256 hashes, ordered from the leaf level to the root level.

### Proof Semantics

A membership proof establishes that a specific key-value pair is consistent with the supplied commitment root.

For membership verification, the initial commitment is:

```text
Keccak256(0x00 || key || value)
```

A non-membership proof establishes that the queried key resolves to the designated empty-leaf commitment within the supplied tree root.

For non-membership verification, the initial commitment is:

```text
Keccak256(0x02)
```

The Solidity verifier requires the supplied value to be zero when `exists == false`.

Both proof types reconstruct the root using the supplied sibling path and key bits. Verification succeeds only when the reconstructed root equals the expected root.

## Solidity Verification

The Solidity contract exposes a stateless verification interface:

```solidity
function verify(
    bytes32 root,
    bytes32 key,
    bytes32 value,
    bool exists,
    bytes32[256] calldata siblings
) external pure returns (bool);
```

The verifier:

1. Constructs the initial leaf or empty-leaf commitment.
2. Processes the 256 sibling hashes in bottom-up order.
3. Determines child ordering from the corresponding key bit.
4. Computes each parent commitment using domain-separated Keccak-256.
5. Compares the reconstructed commitment with the supplied root.

The contract uses Solidity `0.8.24` with the optimizer enabled at 200 runs.

## Cross-Language Compatibility

The repository includes Go-generated proof vectors consumed by Solidity tests.

These fixtures exercise the same commitment format, leaf hashing, sibling ordering, and root reconstruction across both implementations.

The compatibility tests cover:

- Membership proofs generated in Go and verified in Solidity
- Non-membership proofs generated in Go and verified in Solidity
- Rejection of modified proof data

The test suite uses two membership vectors and one non-membership vector.

This verifies compatibility for the included fixtures; it does not constitute exhaustive equivalence testing across all possible tree states.

## Security Considerations

### Commitment Integrity

The commitment construction relies on the cryptographic properties of Keccak-256 and the unambiguous encoding of domain-separated node types.

The verifier reconstructs the complete 256-level path and rejects proofs that do not reproduce the supplied root.

### Root Authenticity

The verifier accepts the expected root as a function argument.

A successful result establishes consistency with that root; it does not establish that the root is authoritative, finalized, or associated with a trusted state transition.

Applications integrating this verifier must independently authenticate and manage accepted roots.

### Proof Encoding

Proofs use a fixed-size sibling array and a deterministic bit-order convention.

Integrations must preserve the exact key encoding, hash domain prefixes, sibling ordering, and non-membership semantics used by this implementation.

### Resource Considerations

Every Solidity verification processes 256 tree levels.

The fixed-depth construction favors predictable verification behavior over compressed proof size or minimal execution cost. Gas consumption should be assessed against the requirements of the integrating protocol.

### Assurance Scope

The repository contains automated correctness, compatibility, and negative tests.

It has not undergone an independent security audit or formal verification. Passing tests and successful Etherscan source verification do not establish production security.
